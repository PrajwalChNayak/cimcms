# CIMCMS LED Controller V0.5.1-dev1

## Purpose
This development build adds a Serial Monitor administration interface for the existing single-room Room Manager and Device Registry, plus LED-controller relay assignment commands.

It is based on the uploaded `CIMCMS_LED_Controller(8).zip` source. Existing scheduler, RTC, keypad, OLED, Wi-Fi, WS2812, relay simulation, and permanent manual-override source has been retained.

## Important scope
- This build manages one active room record (`ROOM-001` initially). It does not introduce zones or multi-room storage.
- Device identity is independent of relay assignment.
- This firmware can assign only the 16 relay outputs owned by the LED Controller.
- LED Controller relay assignments are supported for `lighting` and `lock` devices.
- Other controller types can be registered as metadata, but their physical outputs must be assigned by their own controller firmware.
- A device can have up to four LED-controller relay assignments.
- A relay channel has one registered owner. Duplicate assignments are rejected even if the existing device is disabled.
- The keypad/OLED menu remains the existing operational menu. Device registration and assignment are currently performed through Serial Monitor; a dedicated local OLED/keypad device-management workflow is a later implementation step.
- Relay backend remains controlled by the existing `RELAY_SIMULATION_MODE` setting. This build does not enable physical relay outputs.

## Build
1. Extract this ZIP.
2. Open the folder containing `platformio.ini` in VS Code.
3. Select PlatformIO environment `esp32dev`.
4. Run **Build**.
5. If build succeeds, upload and open Serial Monitor at 115200 baud.

The package is source-only and excludes `.pio` build artifacts. This environment did not have PlatformIO installed, so this version has not been compiled here. Build it locally before flashing.

## Serial commands

### Room
```text
room show
room configure ROOM-001 "Mushroom Cultivation Room" enabled
room configure ROOM-001 "Mushroom Room" disabled
```
Changing the room ID is rejected while devices are registered, to avoid leaving devices attached to an obsolete room ID.

### Device registration
```text
device add LIGHT-01 "Light 01" lighting led relay
device add LOCK-01 "Entry Lock" lock led relay
device add DAMP-01 "Damper 01" damper damper relay
device list
device show LIGHT-01
device rename LIGHT-01 "Main Lighting"
device enable LIGHT-01 off
device enable LIGHT-01 on
device remove LIGHT-01
```
Valid device types: `lighting`, `lock`, `damper`, `humidifier`, `fan`, `sensor`, `other`.

Valid controllers: `led`, `damper`, `humidifier`, `environmental`.

Valid output types: `relay`, `gpio`, `pwm`, `bus`, `none`.

### LED Controller relay assignment
```text
relay assign LIGHT-01 1
relay assign LIGHT-01 2
relay unassign LIGHT-01 2
device show LIGHT-01
```
Assignments are saved to NVS through Device Registry. Assignment is allowed only to a device registered with `controller=led` and `output=relay`. Relay numbers must be 1–16. Each device supports up to four assigned channels.

### Existing operational commands
```text
help
status
relay 1 on
relay 1 off
relay 1 toggle
all off
auto test status
override status
```

## Suggested validation sequence
Start with no registered devices:
```text
room show
device list
```

Register a lighting device and assign a channel:
```text
device add LIGHT-01 "Light 01" lighting led relay
relay assign LIGHT-01 1
device show LIGHT-01
device list
```

Verify duplicate ownership is rejected:
```text
device add LIGHT-02 "Light 02" lighting led relay
relay assign LIGHT-02 1
```
The second assignment should fail because R1 already belongs to `LIGHT-01`.

Verify persistence:
1. Power-cycle the ESP32 without erasing NVS.
2. Run `device list` and `device show LIGHT-01`.
3. Confirm the assignment to R1 remains.

Verify rename/enable/unassign/remove:
```text
device rename LIGHT-01 "Main Light"
device enable LIGHT-01 off
device show LIGHT-01
device enable LIGHT-01 on
relay unassign LIGHT-01 1
device remove LIGHT-01
device list
```

## Known limitations / next work
- No dedicated OLED/keypad device registration screens yet.
- No production schedule association in Device Registry yet.
- Device registration is metadata only; assigning a relay does not automatically alter existing manual/scheduler control policy.
- No command routes for remote MQTT management have been added.
- No multi-room database or zones.
- No physical relay-board validation; keep simulation enabled until relay boards are safely reconnected and verified.
